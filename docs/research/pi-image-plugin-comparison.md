# Pi image plugin comparison

## Executive verdict

**Direct substitutes:** `pi-image-preview` and `pi-paster`. `pi-image-preview` is the same draft-path-to-model-image pipeline from which `pi-image-view` was forked; `pi-paster` independently replaces paths with markers and attaches images. **Complements:** `pi-screenshots-picker` discovers/stages existing screenshots; `@m64/pi-screenshot-tools` captures the desktop and returns tool images; `@yieldcraft/screenshot-paste` is a pi-web workspace gallery. Their overlap is input/preview, not durable TUI history identity. [pi-image-preview marketplace](https://pi.dev/packages/pi-image-preview) [pi-paster marketplace](https://pi.dev/packages/pi-paster) [picker marketplace](https://pi.dev/packages/pi-screenshots-picker) [screenshot-tools marketplace](https://pi.dev/packages/@m64/pi-screenshot-tools) [screenshot-paste marketplace](https://pi.dev/packages/@yieldcraft/screenshot-paste)

**Recommendation:** keep `pi-image-view` as the focused default for privacy-conscious, long-running TUI sessions. It uniquely combines compact model payloads, persistent clickable history, content-addressed deduplication, and non-destructive context clearing. Borrow pi-paster’s atomic-marker editor behavior and picker’s lazy thumbnail loading, but do not copy pi-paster’s default path disclosure or original-resolution payload policy.

## Implementation and performance

`pi-image-view` pays CPU/I/O once per changed editor text, asynchronously reads at most 50 MiB, then caches a resize promise per tracked image. Submission waits for all thumbnails, persists the exact submitted bytes, and hashes those bytes, so identical thumbnails deduplicate. Rendering transmits base64 in 4 KiB chunks and explicitly deletes prior Kitty IDs. Costs scale with image count and encoded bytes; the 250 ms poll is idle-wake overhead, but unchanged text exits immediately. [image loading](https://github.com/alchemistklk/pi-image-view/blob/main/src/image-content.ts) [`ensurePreview`/`scanEditorText`](https://github.com/alchemistklk/pi-image-view/blob/main/src/extension-runtime.ts) [`putImageBlob`](https://github.com/alchemistklk/pi-image-view/blob/main/src/blob-store.ts)

The supervisor’s controlled **20-image** A/B makes the payload trade-off concrete. Current 480 px thumbnails used **4,772 totalTokens**; pi-paster-equivalent originals used **37,046**, about **7.8×** as many. Warm times were current **Luna 7.512 s / Sol 11.808 s / Terra 9.179 s**, versus originals **9.062 / 9.433 / 10.794 s**. These are single runs, not p50/p90: Sol’s reversal demonstrates provider/cache variance, so latency ordering is not established. The defensible measured conclusion is the ~7.8× token difference, not a universal speedup. The broader published snapshot is likewise explicitly single-run. [pi-image-view marketplace benchmark](https://pi.dev/packages/pi-image-view)

Pi-paster’s source contradicts its “32 MB request cap” comment: optimization enforces only 5 MiB **per attachment**, with no aggregate request accounting. It also skips Sharp entirely for inputs ≤256 KiB, so an unusually well-compressed image over 8000 px can bypass the dimension check; missing Sharp returns originals silently, and the final ladder may still return an over-limit image. Its JPEG ladder preserves more visual detail than 480 px, but increases upload, provider vision tokens, retained context, and memory. [`optimizeImageBytes`](https://github.com/beowulf11/pi-paster/blob/main/src/optimize-image.ts) [`imagesForTextOptimized`](https://github.com/beowulf11/pi-paster/blob/main/src/image-utils.ts)

Picker’s lazy strategy is strong: ≤300 KiB previews load synchronously, larger files asynchronously, >5 MiB receive no thumbnail, and nearby entries warm on demand. However, staging synchronously reads and base64-encodes the full file, with no model-resolution optimization. [`startThumbnailLoad`, `loadThumbnail`, `warmThumbnailsAroundCursor`](https://github.com/Graffioh/pi-screenshots-picker/blob/main/index.ts)

A source/README mismatch matters for screenshot-paste: the checked code installs a global paste observer, processes each pasted image to ≤1600 px, and always attempts a separate `.pi-web/paste` gallery copy while allowing native paste through; the marketplace says it “does not duplicate” native capture. Trust the code for this version: gallery persistence adds browser canvas work and disk bytes, and private shadow-DOM polling every 3 s is brittle. [`doPaste`, `processImage`, `CHAT_POLL_INTERVAL_MS`](https://github.com/marcuspocus/screenshot-paste/blob/main/pi-web-plugin.js) [contradictory marketplace text](https://pi.dev/packages/@yieldcraft/screenshot-paste)

## Patterns worth borrowing

1. **Atomic marker navigation/deletion** from pi-paster, preferably without replacing the whole editor; its segmentation and one-step deletion are better than character-wise deletion. [`segmentTextWithAtomicImages`, `handleAtomicPlaceholderDelete`](https://github.com/beowulf11/pi-paster/blob/main/src/editor.ts)
2. **Lazy neighborhood thumbnail loading** and explicit loading/error states from the picker for a future history browser. [picker source](https://github.com/Graffioh/pi-screenshots-picker/blob/main/index.ts)
3. **Optional quality mode:** retain 480 px default, but allow a bounded “detail” payload rather than pi-paster’s near-original default.
4. **Semantic history compaction:** pi-paster’s non-destructive fork-and-summarize concept is useful, but use collision-resistant image hashes; its key is only MIME + base64 length + first 48 characters. [`imageKey`, `registerImageCompressionCommand`](https://github.com/beowulf11/pi-paster/blob/main/src/compress.ts)

## Risks in `pi-image-view`

- **Marker identity is only draft-scoped:** `resetDraft` resets numbering to 1 after every submit, so many history turns can display `[Image #1]`; links differ, but labels are ambiguous. [`resetDraft`](https://github.com/alchemistklk/pi-image-view/blob/main/src/extension-runtime.ts)
- **Privacy is provider-safe, not export-safe:** absolute blob paths remain in session JSONL and reveal username/layout; links are non-portable. [marketplace privacy section](https://pi.dev/packages/pi-image-view)
- **Unbounded disk retention:** content dedupes, but automatic GC is disabled. [blob lifecycle](https://pi.dev/packages/pi-image-view)
- **Fail-open payload:** resize/PNG conversion failure sends and stores the original, potentially up to the 50 MiB read limit; this can negate model limits and tmux transmission safety. [`resizeForPreview`](https://github.com/alchemistklk/pi-image-view/blob/main/src/preview-resize.ts) [read limit](https://github.com/alchemistklk/pi-image-view/blob/main/src/image-content.ts)
- **Detail loss:** 480 px is excellent for UI overview/token cost but can impair tiny text, dense diagrams, or forensic pixels; users need an explicit detail escape hatch.
- **Parser/platform gap:** path extraction recognizes Unix absolute/home/relative paths, not native Windows drive or UNC forms, despite Windows/WSL install guidance. [`IMAGE_PATH_RE`](https://github.com/alchemistklk/pi-image-view/blob/main/src/image-paths.ts)
- **Heuristic terminal detection:** Kitty-in-tmux is inferred from environment variables and writes escape sequences directly to stdout; SSH/nested-terminal false positives remain possible. [`detectImageProtocol`](https://github.com/alchemistklk/pi-image-view/blob/main/src/image-gallery.ts)

## Packaging and maintenance snapshot

Marketplace package sizes are `pi-image-preview` **35.3 KB**, `pi-paster` **361.5 KB**, picker **1.1 MB** (its sole production dependency is `glob`), screenshot-paste **57.7 KB**, and screenshot-tools **721.7 KB**; `pi-image-view` npm metadata reports **54,488 unpacked bytes/15 files**. These are package bytes, not runtime memory. [preview](https://pi.dev/packages/pi-image-preview) [paster](https://pi.dev/packages/pi-paster) [picker](https://pi.dev/packages/pi-screenshots-picker) [web plugin](https://pi.dev/packages/@yieldcraft/screenshot-paste) [tools](https://pi.dev/packages/@m64/pi-screenshot-tools) [npm metadata](https://registry.npmjs.org/pi-image-view)

All are young 2026 packages, so version count is a weak maturity signal. The inspected clones also lag marketplace in places (`pi-screenshot-tools` manifest 0.1.8 vs marketplace 0.1.9), and screenshot-paste’s code banner says `0.4.0-dev` inside a 0.4.3 package. Pin versions and validate behavior from shipped source, not README text alone.
